工業自主機器人 ／ Traceability · Auditability · Runtime Assurance
技術調研 · v2 · 2026-08-27 · Continuous Assurance
Industrial Embodied AI · Trustworthy Autonomy

AI機器人自主工作還不夠，
還要能追、能查、能證明。 從 imitation learning、Diffusion Policy、VLA 到 robot foundation model：學習式機器人如何跨越「高成功率 demo」與「可被工業採用」之間的可信任落差。

本調研的核心判斷是：learned policy 本身通常不足以直接滿足工業場域的可追溯性與可稽核性要求。較具落地性的方向，是將 AI 的適應性與泛化能力置於可驗證的任務語意、技能契約、運行時安全邊界與完整證據鏈之中，形成 governed autonomy。

核心差距
Policy ≠ Skill

神經策略能輸出動作，不等於一個具版本、限制、適用域與失效處置的工業技能。

工業要求
Evidence Chain

需求、資料、模型、決策、動作、品質結果與異常處置必須能串成可重建的證據鏈。

主流補強
Runtime Assurance

不要求黑盒 policy 全面可證明，而是在執行時以 safety filter、shield、monitor 約束行為。

研究定位
Bounded Autonomy

讓 AI 在明確限制、驗證域與可回復機制內自主，而不是追求無界限 autonomy。

00執行摘要

本節以決策者角度回答三個問題：工業界要求什麼、熱門學習式機器人目前缺什麼、最值得投入的技術缺口是什麼。

「高任務成功率」與「可被工業稽核」是兩個不同的工程目標。本調研綜合 NIST、ISO、EU AI Act、robot learning / formal methods 與業界安全框架後之判讀。
結論 01

可追溯性不是只有 log

工業 traceability 要能從需求、任務規劃、技能與模型版本一路追到感知輸入、實際動作、品質結果、異常與 recovery；NIST 也把開發流程、訓練資料來源、系統過程與結果的可追蹤紀錄視為 auditability 機制的一部分。

結論 02

可稽核性要求「可判斷是否合理」

Auditability 比 reconstruct event 更進一步：要知道此動作是否符合任務規格、安全限制、模型適用域與部署核准條件，並能由第三方或 QA 人員檢視證據。

結論 03

IL / Diffusion / VLA 本身通常不夠

它們可以提供強大的 visuomotor 或 task-level 能力，但 end-to-end 動作是高維神經網路映射，通常缺乏人可讀的規則鏈、有效域宣告與形式化約束，因此比較容易做到 execution logging，而非完整 industrial auditability。

結論 04

工業落地最可行的是「智慧與保證分層」

讓 VLA / policy 負責提出 plan 或 nominal action，再由 skill contract、runtime monitor、safety filter、certified controller 與 evidence layer 做限制與留證，形成 bounded / governed autonomy。

01工業語境下的可追溯性與可稽核性

兩個詞常被混用。工程上最好將 traceability 視為「可重建」，auditability 視為「可重建＋可評估」。

A. 可追溯性 Traceability：能重建「發生了什麼」

工業自主機器人的 traceability 應至少涵蓋：需求來源、任務計畫、skill ID / version、policy / model version、training / validation data lineage、感知輸入、機器人命令、執行軌跡、品質結果、異常事件與人員介入。重點不是單點資料存在，而是事件之間具可查詢的關聯。

工單、產品型號、品質規格、風險限制

02

任務分解、技能選擇、前置條件

NIST AI RMF Playbook 明確提及 development process、training data sourcing，以及 AI processes / outcomes 的 logging 以支援 auditability。[1][2]

02Learned Autonomy 的四個 Industrial Assurance Gap

問題不應只被描述成「黑盒模型不易解釋」。真正影響工業採用的是四種不同的 assurance gap：決策不可讀、能力邊界不清、執行失敗難以及時偵測，以及模型／資料更新後既有證據是否仍然有效。

Gap 01

Decision opacity｜為什麼選這個 plan / skill / action？

VLA、IL 與 Diffusion Policy 能產生有效行為，但其內部映射通常不是人可直接稽核的規則鏈。工業系統因此需要把可稽核焦點移到 task representation、skill selection、constraints 與執行證據。

Gap 02

Competence uncertainty｜什麼情況下它仍然有效？

一個 learned skill 必須宣告 validated domain：零件、治具、公差、感測器、光照、姿態、速度與接觸條件。OOD / uncertainty 機制負責判斷當前狀態是否仍位於已驗證能力範圍。

Gap 03

Runtime failure｜任務正在失敗時能不能及時知道？

安全邊界沒有被突破，不代表任務仍然健康。插入卡滯、抓取滑移、fixture 偏移或 visual servo 漂移可能仍處於 safety limit 內，卻已經高度可能失敗。

Gap 04

Model evolution｜更新後原有 assurance evidence 還成立嗎？

retraining、資料增補、相機／治具更換甚至 process tolerance 改動，都可能改變 policy 行為。工業部署真正的瓶頸可能從程式撰寫轉為 change impact analysis、regression、re-validation 與 re-qualification。

Learning may reduce programming cost, but it can increase assurance and change-management cost.換型是否真的變快，取決於 learning time 加上 validation / assurance time，而不是只看模型訓練時間。
四個概念不要混為一談

OOD Detection 問「我有沒有看過這種情況？」；Uncertainty 問「我有多沒把握？」；Safety Monitoring 問「目前動作是否會跨越危險邊界？」；Failure Detection 則問「即使仍安全，任務是不是已經偏離正常成功軌跡？」。

03為什麼工業機器人特別在意這件事？

製造場域不是只看 task completion。品質責任、功能安全、維護、換型、版本管理與事故調查，都要求系統在全生命週期留下可核對證據。

品質 QA

結果要能與製程規格對上

不是「成功抓到」就算成功，而是姿態、力、扭矩、鎖付值、插入深度、檢測結果都要落在製程規格內。

安全 Safety

高成功率不能替代 hazard control

一次低機率動作失敗若可能造成人員傷害或設備損壞，就需要獨立於 task reward 的 safety mechanism。

維運 Operations

模型更新不能是黑箱替換

必須知道更新了哪個模型、用什麼資料訓練、驗證哪些工件／情境、何時發布與何時回滾。

責任 Accountability

事故要能重建

需要證明當時的 observation、skill、policy、constraints、override、human intervention 與結果，而非只保留影片。

對工業 autonomous robot，更實際的目標不是「Explain every AI decision」，而是：
Every autonomous action must be attributable, bounded, monitorable, reproducible and auditable.

04學術界正在怎麼處理？

目前可歸納成四條互補路線：可解釋／結構化策略、formal methods、runtime assurance，以及 uncertainty / OOD / human intervention。

01
Interpretable / Structured Policy

增加可閱讀的 task graph、symbolic state、language rationale 或 concept representation。優點是理解性高，但難直接對低階 continuous action 提供安全保證。

02
Formal Specification & Verification

用 temporal logic、model checking、reachability、formal synthesis 等方式描述「policy 應滿足什麼」，並驗證或導引學習。2026 survey 將領域整理為 policy learning 與 policy verification 兩大柱。[7]

03
Runtime Assurance / Safety Shield

讓 learned policy 產生 nominal action，再用 safety filter、control barrier function、constrained optimization 或 shield 在 runtime 限制不可接受動作。SHIELD 與 Adaptive Shielding 均屬此類。[9][10]

04
Failure / Anomaly / Progress Detection

監控 execution trajectory 是否偏離成功軌跡，例如 force-time profile、grasp slip、visual progress、expected state transition 或 learned failure predictor。此類監測處理的是 task health，而非只看是否跨越 safety limit。

05
Uncertainty / OOD / Intervention

建立 competence boundary：當 observation 或 state 超出 validated domain，停止、降級、re-perception、retry 或請求人員介入；Diff-DAgger 即利用 uncertainty 觸發 expert query。[8]

重要趨勢Formal methods 社群並不是假設「整個 end-to-end vision policy 很快就能完全形式驗證」。更實際的研究方向，是把可形式化的 specification、局部可驗證模組與 runtime monitoring組合起來，在 scalability 與 assurance 之間取平衡。[7]

05業界、標準與法規如何看待？

共同訊號相當一致：不是拒絕 AI autonomy，而是要求 autonomy 在可界定限制、風險管理、技術文件、logging、V&V 與安全層之中運作。

法規層級判讀對工業機器人，本調研建議把 EU Machinery Regulation 2023/1230 放在 EU AI Act 之前理解。前者直接面對 machinery、control system、self-evolving behaviour、defined task / movement space、software modification 與 safety-related logging；AI Act 則補充特定 AI system 的治理、風險管理、透明與紀錄義務。
EU · 2023
Machinery Regulation 2023/1230：autonomy、software evolution 與 machinery safety 正式接軌

Annex III 要求具 fully or partially self-evolving behaviour / logic 且以不同 autonomy level 運作的控制系統，不得執行超出 defined task and movement space 的動作，並要求可修正以維持 inherent safety；對 software-based safety systems 的 safety-related decision process 亦要求 recording。另對 safety software version upload 設有 tracing-log 要求。[15]

ISO · 2021
ISO/TR 22100-5: AI/ML machinery 必須在 specified limits 內討論風險

文件處理的是設計在特定限制內運作的 AI/ML machinery；若 AI 被設計成超出指定限制並可能產生不可預測 effects，則不在該文件適用範圍。這可視為 bounded autonomy 的標準化訊號。[3]

ISO · 2024
ISO/IEC TR 5469：明確區分 AI 與 safety function 的組合方式

涵蓋 AI 位於 safety-related function、以 non-AI safety-related function 保護 AI-controlled equipment，以及用 AI 協助 safety function 開發三種情境。[4]

EU · 2024/26
EU AI Act Article 12：high-risk AI 要有自動事件紀錄與適當 traceability

法規要求 high-risk AI systems 具 automatic recording of events，logging 要支援風險識別、post-market monitoring 與 operation monitoring；Article 13 另要求足夠 transparency 以讓 deployer 適當解讀輸出。[5]

ISO · 2025
ISO 10218-1/-2: 工業機器人安全回到 system / application integration

Part 1 針對 industrial robot 本體，Part 2 針對 industrial robot applications / cells；AI 模型不太可能脫離 robot、tool、fixture、cell、controller 與使用情境單獨完成 assurance。[6]

Google · 2025/26
Gemini Robotics：semantic / physical / operational 多層防護

DeepMind 將安全描述為 Swiss-cheese 式多層 safeguards，並公開表示 VLA 可與 lower-level safety mechanisms 組合；On-Device 版本也提到以 low-level safety-critical controllers 執行動作。[11][12]

DGUV · 2021/26
DGUV：AI 可支援 machinery safety，但現階段不應取代 conventional safety functions

DGUV Test Information 05 提供 AI safety assessment 的一般原則；DGUV Forum 2026 更直接指出，因現行 normative / regulatory requirements 尚不完整，AI 目前可支援 safety functions、但不能取代 conventional safety functions，並要求從 sensor、controller、HMI、環境到 lifecycle 做 whole-system assessment。[16][17]

AMLAS
AMLAS：把 ML assurance 從「模型測試」提升為 lifecycle safety case

AMLAS 以六階段方法把 ML safety scoping、requirements、data management、model learning、verification 與 deployment 串成迭代 assurance process，要求各階段產出可支撐 explicit safety case 的 evidence。它不是 machinery 法規或 system-level safety standard，而是補足 ML component assurance 的方法論。[18][19]

NIST · 2026
Smart Manufacturing Roadmap：trustworthy、explainable、reliable 已成工業 AI 核心障礙

NIST 2026 roadmap 指出 AI/ML 工業部署仍面臨 industrial big data、異質 sensing/control 整合，以及 trustworthy、explainable、reliable operation 的關鍵挑戰。[13]

不要過度延伸標準

上述 ISO/TR 與 AI Act 不代表「使用 Diffusion Policy 的工業機器人必然屬某一法規類別」或「某一特定 neural policy 已獲認證」。它們提供的是風險管理、bounded operation、technical documentation、logging、system-level assurance的方向性要求；實際合規仍須依機器、用途、司法管轄與 safety function 架構判斷。

06建議的工業化架構：Governed Learned Skill + Continuous Assurance

最實際的設計不是試圖讓整個黑盒 policy 變成白盒，而是把智慧、執行監測、功能安全、變更管理與證據治理拆成可管理層次，並讓 assurance 隨模型與製程生命週期持續更新。

Industrial Governed Autonomy Stack
Learned Intelligence
VLM / VLA / Task Planner：理解需求、提出 task plan、選擇 candidate skill；Visuomotor Policy：產生 nominal action / trajectory。
Skill Governance
Skill Contract：preconditions、parameter range、validated domain、success / failure criteria、version、model / data provenance、fallback。
Runtime Assurance
Safety monitor + execution monitor + failure / anomaly detector + uncertainty / OOD + recovery supervisor：不是只有 action filter，而是完整監控 task health 與 competence boundary。
Safety Control
Safety PLC / certified controller / low-level limits：處理獨立於 learned policy 的 safety-related functions、protective stop 與 emergency functions。
Change & Evidence
Change impact analysis + regression / re-validation + event log + data/model lineage + approval / rollback。

B. Runtime Assurance：不只 Safety Filter，而是五種互補能力

R1
Safety Monitoring / Action Admissibility

回答「這個 action 是否會進入危險狀態？」；檢查 collision、速度、workspace、力／扭矩 hard limit，必要時 reject / project / shield。

R2
Task Execution Monitoring

回答「執行是否按照預期進展？」；監看 expected state transition、pose progression、contact sequence、visual progress 與時間窗。

R3
Failure / Anomaly Detection

回答「任務是否已偏離成功軌跡？」；例如 insertion force profile 異常、grasp slip、fixture 偏移。它可能在仍未跨 safety limit 時就觸發 recovery。

R4
Uncertainty / OOD / Competence Boundary

回答「當前 observation 是否仍屬於 validated domain？」。

R5
Recovery Supervisor

依事件類型採 retry、re-perception、alternate skill、safe stop 或 human intervention，並保留 reason code。

典型案例插入時 Fz = 28 N，若 safety hard limit 為 40 N，Safety Filter 可能認為仍可執行；但若正常製程 envelope 通常低於 12 N，failure detector 應已判斷卡滯／錯位風險升高。安全 ≠ 任務健康。

C. Model / Process Change Management：更新不是部署細節，而是 re-assurance 問題

Learned robot 的部署成本不能只計算 demonstration 與 training。每一次 model、data、sensor、tool、fixture 或 process tolerance 變更，都應先做 change impact analysis，再決定既有 validation evidence 是否仍有效。

這也是 EU Machinery Regulation 2023/1230 與 AMLAS 值得放進同一份調研、但角色不同的原因：前者提醒 machinery / safety software / autonomous control 的 lifecycle 與 configuration traceability；AMLAS 則提供 ML component 從 safety scoping、data、learning、verification 到 deployment 的 evidence-building 方法。[15][18][19]

07對「機器人任務自主規劃與決策」研究的建議

若研究計畫只寫「VLM/VLA 任務理解 → 自動規劃 → Diffusion Policy 執行」，很容易與國際 embodied-AI demo 同質化。工業化差異點應放在「可稽核 autonomy」。

研究主軸 A

Auditable Task Planning

任務計畫採結構化 representation；每個 subtask 有來源、precondition、constraint 與理由；planner output 可對應製造需求與設備能力。

研究主軸 B

Governed Skill Learning

把 learned visuomotor policy 封裝為帶 contract 的 skill：建立 validated domain、model/data lineage、版本、成功／失敗定義與可替換 policy。

研究主軸 C

Runtime Failure-aware Assurance

除 safety monitor 外，加入 execution progress、failure / anomaly prediction、uncertainty / OOD 與 recovery supervisor，區分「危險」與「任務正在失敗」。

研究主軸 D

Continuous Assurance & Change Management

建立 model / data / process change impact analysis、regression 與 re-validation，讓模型更新有 evidence scope、release gate 與 rollback。

08結論：工業 Embodied AI 的競爭點將從「會做」走向「可信任地做」

Robot foundation model 提高了能力上限，但製造現場的採用門檻仍由可靠性、安全、可管理性與責任證據決定。

真正適合工業化的 autonomous robot，不一定需要把神經網路完全「解釋清楚」；但它必須能證明：
我是誰的版本、我在什麼範圍能做、我為何被允許做、我做了什麼、我有沒有超界、結果是否合格、出事如何重建。

因此，最值得投入的研究缺口不是再做一個更大的 policy，而是建立一個能承接 learned intelligence 的 Industrial Autonomy Layer：以 task traceability、skill governance、runtime assurance、safety constraints、validation 與 audit trail，把 frontier robotics intelligence 轉換成可部署、可驗證、可維運的工業自主能力。
